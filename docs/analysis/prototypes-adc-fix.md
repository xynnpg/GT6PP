# `Prototypes.adc`: producer, `loadPrototype` path, and the `HOTREAD8` spin

**Date:** 2026-10-31
**Scope:** GT6 US `BCUS98296` v1.00, `work/bin/EMAIN.elf`, extracted
`work/gt6_vol`, and the measured runs `work/pfstrace.err`,
`work/long_run.err`, `work/fix_run.err`, `work/gt6_calltrace.log`.
**Read-only analysis** except for the new installer tool
`tools/gt6_install_companion_script.py` and the ADCH disassembler
`tools/adch_disasm.py`. No relift, build, or `gt6.exe` run was performed.
**Policy:** `third_party/PDTools/AGENTS.md` was not read or used.

## 0. Verdict

| Question | Finding |
|---|---|
| What is `products/gt6/script/Prototypes.adc`? | A **compiled Adhoc v12 script** (ADCH) that is the companion of `Prototypes.mwidget`. It is built offline from a `Prototypes.ad` source, not generated by the retail runtime. |
| Is it in GT.VOL / the extracted tree / the key map? | **No.** The v1.00 disc has only `Prototypes.mwidget` (MPRJ, 5,827 bytes). No case variant, no cache key, no alias. |
| Does the guest compile the MPRJ into ADCH in memory? | **No evidence, and the code says no.** `0x5EA000` validates the `MPRJ` magic and deserializes a project; there is no ADCH emitter anywhere in `EMAIN` (only the reader `0x9CD410`, only the `ADCH` literal). |
| Does a first-run install write it? | **No.** `DataInstallUtil.adc` and the HDD game-data installer copy existing game data and write `/APP_DATA/installed00.dat`; they do not compile or write scripts. |
| What is the real producer? | An **official GT6 update/patch volume**. The game contains `PDIPatchFileSystem` and the patch root `/patch/PATCHPACKAGE/`; the user must supply the update (1.01+ / final 1.22) that contains the real ADCH. |
| Is the failed open the cause of `HOTREAD8` at guest `0x19`? | **Not proven, and probably not directly.** `func_009E191C` walks the global registry at `0x15D5F68`; its constructor ran from `.ctors` #568. The failed `.adc` open is followed by successful cursor asset loads and then the empty `K/W2` cache before the first tid-5 null calls. The missing script is a real functional gap, but the null tree node is a separate registry/cache failure. |
| Fix | **Do not fabricate/alias ADCH.** Install the genuine `Prototypes.adc` from the official update with the new validator/installer. If the update is unavailable, leave the request to fail cleanly and fix the `K/W2`/registry path separately. |

## 1. The file is genuinely missing from v1.00

Independent checks agree:

- `work/gt6_volume_entries.txt` (32,591 entries) contains exactly one
  Prototypes file:

  ```text
  products/gt6/script/Prototypes.mwidget - Flags: Compressed | FileIndex: 35 (K/6I) ...
  ```

- `work/gt6_pfs_keymap.tsv` maps `K/6I` only to `Prototypes.mwidget`.
- `work/gt6_vol/products/gt6/script/` contains only `MenuClassDefine.adc`
  and `Prototypes.mwidget`.
- `Prototypes.mwidget` begins `4D 50 52 4A` (`MPRJ`), not `41 44 43 48`
  (`ADCH`). It is a serialized widget/project tree, not a script.

The resident `MenuClassDefine.adc` symbol table names the missing module
explicitly:

```text
[ 231] loadPrototype
[ 232] Prototypes
[ 233] prototypes
[ 234] registerPrimitives
```

## 2. `loadPrototype("Prototypes")` and `registerPrimitives`

`MenuClassDefine.adc` is the compiled form of
`products/gt6/script/MenuClassDefine.ad` (symbol 0). Its top-level frame
(820 instructions) ends at line 177/178:

```text
0302C| 177| 807| VARIABLE_EVAL manager, manager, idx=1
0303B| 177| 808| ATTRIBUTE_EVAL loadPrototype
03046| 177| 809| STRING_CONST Prototypes
0304D| 177| 810| CALL 1
03056| 177| 811| VARIABLE_PUSH prototypes, idx=1
03065|   0| 812| ASSIGN_POP
0306A| 178| 813| VARIABLE_EVAL manager, manager, idx=1
03079| 178| 814| ATTRIBUTE_EVAL registerPrimitives
03084| 178| 815| VARIABLE_EVAL prototypes, idx=1
03093| 178| 816| CALL 1
0309C|   0| 817| POP
030A1|   0| 818| LEAVE depth=0, rewind=1
030AE|   0| 819| SET_STATE 0
```

Native registration table (`0x5F0E04`, string -> OPD):

| Name | OPD | Code |
|---|---|---|
| `registerPrototypes` | `0x14C43B0` | `0x5F65B0` |
| `registerPrimitives` | `0x14C43B0` | `0x5F65B0` (same wrapper in this build) |
| `loadWidget` | `0x14C4408` | `0x5FADE4` |
| `loadPrototype` | `0x14C4408` | `0x5FADE4` (same wrapper) |
| `hasPackageEntry` | `0x14C4398` | `0x5F27F0` |
| `loadPackage` | `0x14C43C8` | `0x5F7970` |

### 2.1 `loadPrototype` is the MPRJ loader, not a compiler

`0x5FADE4` (`loadPrototype`):

- At `0x5FAE14..0x5FAE24` it appends `.mwidget`
  (string `0x1053A38`) for the one-argument form.
- It calls `0x5FABF0` at `0x5FAFA0`.
- `0x5FABF0` calls the project loader `0x5F3A44` at `0x5FAC8C`.

`0x5F3A44` opens the project and probes its companion script:

- `0x5F3FAC` constructs an `HFileReader`;
- `0x5F3FE4` calls `HFileReader::open` (`0x9BB11C`) on the `.mwidget`
  path;
- `0x5F3FEC` calls `0x5EA000`, which checks the four bytes at the start of
  the stream against the literal `MPRJ` at `0x10531D0`
  (`0x5EA16C..0x5EA184`);
- `0x5F4078..0x5F4094` copies the name and appends `.adc`
  (literal `0x1053910`);
- `0x5F421C` calls `0x9F6E98` to open/stat the `.adc`;
- if that fails, `0x5F4234..0x5F42A0` stores the path under the
  `__node_script_path__` attribute and returns success.

So the project loader **tolerates** the missing `.adc`; it does not compile
the MPRJ.

### 2.2 The actual `.adc` reader

`0x5F299C` is the script reader:

- `0x5F29DC..0x5F29F0` appends `.adc` (literal `0x1053910`);
- `0x5F2E44` calls `HFileReader::open` (`0x9BB11C`);
- `0x5F2CB0` calls `0x9CD410` (`ADCH` header reader / parser).

`0x5F2D74` wraps it and calls it at `0x5F2DC0`; `0x5F2D74` is reached from
`0x5DB250`. This is a read/parse path only.

`hasPackageEntry` (`0x5F27F0`) also builds `path + .adc` and opens the
reader, but only to test whether the entry exists. Either the package probe
or the script reader produces the measured request; both are readers.

## 3. Why there is no MPRJ -> ADCH fallback

1. `0x5EA000` validates `MPRJ` and constructs the project/composite objects.
   It has no call to `0x9CD410` or to any writer.
2. The only `ADCH` references in `EMAIN` are the reader strings
   (`0x1095058`, `0x1095170`) and the comparison at `0x9CD478`.
   There is no `ADCH012` magic literal for a writer.
3. `save_script`, `merge_mode`, and `link_mode` are **boolean project
   attributes**, not a compiler:
   - `save_script` OPD `0x14C42D8` -> `0x5EFCF4` reads a byte at project
     `+0x58`;
   - `link_mode` OPD `0x14C42E0` -> `0x5EFE48` reads `+0x57`;
   - `merge_mode` OPD `0x14C42E8` -> `0x5EFF84` reads `+0x56`.
4. `registerPrimitives`/`registerPrototypes` (`0x5F65B0`) calls `0x5F612C`
   at `0x5F6618`, which iterates the project class-name table and calls
   `0x5F5790` to register each class. It does not open a `.adc` or emit code.
5. The only `.adc` producer would be an external compiler (GTAdhocToolchain
   in PD's build pipeline), not the retail `EMAIN`.

## 4. Install / update producer

### 4.1 The first-run installer is game-data only

`scripts/gt6/util/DataInstallUtil.adc` contains:

```text
FUNCTION_DEFINE setInstalled
FUNCTION_DEFINE isInstalled
FUNCTION_DEFINE checkAllFiles
FUNCTION_DEFINE installAllFiles
FUNCTION_DEFINE execute
FUNCTION_DEFINE doInitialInstall
```

`setInstalled` writes only the marker:

```text
00C08| 56| 22| VARIABLE_EVAL pdistd, WriteFile
00C18| 56| 23| STRING_CONST /APP_DATA/installed00.dat
00C1E| 56| 24| STRING_CONST INSTALLED
00C24| 56| 25| CALL 2
```

`isInstalled` checks the same marker (`0x00D14`). `installAllFiles` copies
file entries (`pdistd.GetFileEntries`, `pdistd.ReadFile`) to `/APP_DATA`.
This is the GT6 game-data install; it does **not** compile scripts and cannot
create `Prototypes.adc`.

### 4.2 The official update patch filesystem

The binary contains the PS3 patch/update path set:

| String / role | Vaddr |
|---|---|
| `/patch/PATCHPACKAGE/` | `0xFB1040` |
| `fsroot`, `BD`, `HDD` | `0xFB1058..0xFB1068` |
| `PDIPFS`, `/APP_DATA`, `/APP_DATA_RAW`, `/APP_CONTENT`, `/APP_CACHE` | `0xFB1070..` |
| `/dev_hdd0`, `/APP_DATA/UPDATING`, `/APP_DATA_RAW` | `0x1097A14` |
| `PDIPFS`, `PDIPFS_bdmark` | `0x1097B70` |
| `PDIPatchFileSystem::PatchInstall` RTTI | `0x1097E14` area |

`0x11B34` returns `/patch/PATCHPACKAGE/`; the PDI app init at `0x11EA8`
registers the `PDIPFS`/`BD`/`HDD` roots. The PS3 firmware installs official
updates into `/dev_hdd0/game/BCUS98296/`; the game then overlays the patch
filesystem. The port maps that guest path to
`work/gt6_hdd0/game/BCUS98296/`.

**Therefore the real producer of `Prototypes.adc` is the official GT6
update/patch volume**, not the v1.00 disc and not a first-run compile. The
expected logical path inside the update is:

```text
products/gt6/script/Prototypes.adc
```

For the current host override the file must end up at:

```text
work/gt6_vol/products/gt6/script/Prototypes.adc
```

For a firmware-style patch install it would live under the extracted update
tree at:

```text
work/gt6_hdd0/game/BCUS98296/...
```

with the update's `PDIPFS` / patch-package layout (`/patch/PATCHPACKAGE/`,
`patchinfo.xml`, `.dat`, `base-path`, `package-path`). The port currently
does not emulate the firmware patch mount itself; the direct extracted-tree
path is the simplest supported route.

### 4.3 HLE gaps that are *not* the producer

- `cellFsAllocateFileAreaWithoutZeroFill` NID `0x7A0329A1` (stub
  `0xF924B0`) is a no-op.
- `cellFsTruncate` NID `0xC9DC3AC5` (stub `0xF92718`) is not registered.

These explain 0-byte `.fdupi` files and belong to the separate PFS
write-through fix. They cannot create `Prototypes.adc`, because there is no
source ADCH to write. `cellGameDataCheck` returning `CELL_GAME_RET_NONE` for
an empty HDD root is also normal; `cellGameCreateGameData` only creates
directories.

The **skipped install step** is the firmware-side official-update install,
not a game HLE call. On a real PS3 the firmware mounts the update package
before `cellGameBootCheck`; the port's `cellGameBootCheck` only reports the
disc game and does not emulate that patch mount. The game-data installer
(`DataInstallUtil`) is a separate, optional copy of BD data to `/APP_DATA`
and never produces ADCH. Therefore neither missing NID in the PFS write path
nor an empty HDD root can explain the absent script; the user must supply
and expose the official update tree.

## 5. The `HOTREAD8` at guest `0x19`

`func_009E191C` at `0x9E191C` contains the exact load:

```text
009E1A18: clrldi r29, r31, 0x20
009E1A1C: lbz    r0, 0x19(r29)   ; effective EA 0x19 when r29 == 0
009E1A20: cmpwi  cr7, r0, 0
009E1A24: beq    cr7, 0x9E1998   ; 0 = not the sentinel, keep walking
```

`r29` is the current node in the global registry at `0x15D5F68`.
`r31` starts as `[[0x15D5F68+0x6C]+4]` (header + root). The byte at `+0x19`
is the node/sentinel flag; a null node yields zero and is treated as a live
node, so the walk keeps reading `0x19`/`0xC` forever.

The global was **constructed at boot**:

- `.ctors` entry 568 is OPD `0x14D9B50` -> `0x97B768` -> `0x97AC90` ->
  `0x9E2428` (map constructor);
- `work/gt6_calltrace.log:510` records
  `[CALL] -> 0x0097B768 ... from=func_000118C8+0x3D0 tid=1`.

So the root is not null because the constructor was skipped. It is null
because a node/child was zeroed, a bucket was cleared, or the registry was
destroyed/corrupted later. Do **not** patch `0x9E191C` to accept NULL; the
node flag is the only sentinel test in this custom tree.

### 5.1 `0x15D5F68` is the built-in type map, not the prototype class table

The Ghidra output confirms the two maps are different:

- `value_compare` (`0x9E191C`) walks `*(uint *)(map + 0x6c)` and tests the
  node byte at `+0x19`.
- `0x9E2428` constructs the map and tail-calls `0x9E1E94(map, 1)`. That
  routine inserts the built-in type objects (the `Short`, `Int`, `Long`,
  `UByte`, ... strings at `0x10961E8..0x1096250`) through
  `0xF448B4` at `0x9E208C`/`0x9E2160`. It does not read `.adc` and does not
  call `registerPrimitives`.
- `registerPrimitives` (`0x5F65B0`) calls `0x5F612C` at `0x5F6618` with the
  project object. `0x5F612C` iterates the project class list and calls
  `0x5F5790(project, 0x22, class_name, ...)` at `0x5F6300`.
  `0x5F5790` looks the class up with `0x5F31A4` at `0x5F57F4`; on a miss it
  creates the class object (`0x5D8FAC`/`0x5D911C`) and calls `0xDFFEF0` at
  `0x5F59B0`, which inserts into a map whose sentinel byte is at **`+0x21`**
  (`0xDFFFB4`), not `+0x19`. It never references `0x15D5F68`.
- `project_loader` (`0x5FABF0`) does call `0x988FF0(&out, key)` at
  `0x5FAC34`, which is the `0x15D5F68` map lookup/insert helper. That is the
  project-path cache lookup, not class registration.

Therefore an empty `0x15D5F68` tree is **not** explained by the missing
`Prototypes.adc` or by a skipped `registerPrimitives` call. `registerPrimitives`
is reached from `MenuClassDefine.adc` line 178 and populates the separate
project/class map; the `+0x19` map is the built-in type registry and is
populated by its static constructor. The `+0x19` null must be treated as a
later corruption/clear and A/B'd separately.

The measured chronology does not make the `.adc` failure the immediate
trigger:

```text
pfstrace.err:6507  open  /products/gt6/script/Prototypes.adc
pfstrace.err:6515  no extracted file
pfstrace.err:6559  open  /projects/gt6/cursor/cursor.mproject   (served)
pfstrace.err:20752 open  /projects/gt6/cursor/cursor.adc        (served)
pfstrace.err:32424 open  .../PDIPFS_bdmark/K/W2                 (empty cache)
pfstrace.err:32440 first tid-5 null call
```

`long_run.err` shows the same order:

```text
1495  serving Prototypes.mwidget
1592  serving cursor.mproject
1700  serving cursor.adc
1780  open K/W2
1784  open K/W2.fdupi
1820  first tid-5 null call
2172  HOTREAD8 spinning on 0x19 ... guest-fn=0x009E191C
```

The failed `.adc` open is therefore a **real script-level gap** but not
proven to be the sole cause of the null registry walk. The empty `K/W2`
cache is the closer measured correlate; the registry null should be A/B'd
after the real `Prototypes.adc` and the PFS write-through are fixed.

## 6. Implemented fix

The correct fix for the **missing file** is not to synthesize it. The new
tool `tools/gt6_install_companion_script.py`:

1. accepts a file or directory from an official update;
2. rejects `MPRJ`, non-ADCH, non-v12, truncated, or implausible files;
3. parses the ADCH symbol table and top-level frame;
4. requires the debug source symbol to be `Prototypes.ad` or
   `_tmp_Prototypes.ad`;
5. copies the verified bytes atomically to the extracted tree, refusing to
   overwrite a different existing file.

Usage:

```powershell
# Does the tree already have it? (expected: no)
python tools\gt6_install_companion_script.py --scan work\gt6_vol

# Validate one official-update file, no copy
python tools\gt6_install_companion_script.py --source <update>\Prototypes.adc --dry-run

# Install for the existing PFS override
python tools\gt6_install_companion_script.py --source <update>\Prototypes.adc

# Or target a firmware-style patch tree
python tools\gt6_install_companion_script.py --source <update>\Prototypes.adc `
  --dest work\gt6_hdd0\game\BCUS98296\USRDIR\...\products\gt6\script\Prototypes.adc
```

The tool is data-faithful: it never writes an ADCH header or code frame of
its own. If the official update is unavailable, it exits with:

```text
no ADCH v12 file with source Prototypes.ad found. Refusing to fabricate one.
```

### 6.1 Verification procedure

1. Install the real file and confirm its SHA-256 with `--scan`.
2. Run the game with `GT6_PFS_TRACE=1`.
3. Expect:

   ```text
   [GT6] pfs override: serving plaintext products/gt6/script/Prototypes.adc (... bytes)
   ```

   and **no**:

   ```text
   [GT6] pfs override: no extracted file for 'products/gt6/script/Prototypes.adc'
   ```

4. Confirm `0x9CD410` accepts the `ADCH012\0` header and the code frame
   (the disassembler `tools/adch_disasm.py` should decode line 177/178 if
   this is the real MenuClassDefine companion; `Prototypes.adc` itself may be
   data-only and have few instructions).
5. Re-test the `0x9E191C` spin independently. If it persists, fix the
   `K/W2`/PFS cache and the registry corruption; do not blame the `.adc`
   alone.

## 7. What not to do

- **Do not** serve `Prototypes.mwidget` as `Prototypes.adc`: `0x9CD478`
  rejects the `MPRJ` magic and the ADCH parser would fail.
- **Do not** alias `cursor.adc`, `MenuClassDefine.adc`, or any other script:
  different symbol tables and module contents would register the wrong
  classes/methods.
- **Do not** hand-build a minimal ADCH. It would only hide the missing
  prototype script, not supply its registrations.
- **Do not** patch `func_009E191C` to treat NULL as a valid node. The null is
  a registry-corruption symptom; returning a fake node would move the fault
  downstream.

## 10. Related work

- PFS raw-source write-through / 0-byte `.fdupi` and the empty `K/W2` cache
  are owned by the PFS fixer; this document does not duplicate that fix.
- The `0x9E191C` registry corruption needs a separate A/B after the real
  `Prototypes.adc` and the PFS cache are working.
- `tools/adch_disasm.py` is the read-only disassembler used to prove the
  `loadPrototype`/`registerPrimitives` sequence; it is not a compiler.
